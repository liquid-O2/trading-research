# Workspace working rules

For trading research, read [START_HERE.md](/workspace/planning/trading-research/START_HERE.md) and the [project instructions](/workspace/trading-research/AGENTS.md) once on entry. Continue from their current state in `/workspace/trading-research`; preserve original `/workspace/data` and `/workspace/sources`. `/workspace/archive` remains excluded. Later user instructions take precedence.

- Keep one current deliverable and observable acceptance conditions tied to the latest user request in the existing checkpoint. The full project catalogue is background scope, not permission to expand the current task. Do not replace a performance repair with research completion or promote a source example or implementation choice into a user requirement. Before investigating, editing, testing or delegating, identify what would fail in the requested outcome if that work were omitted. If nothing would fail, defer it. An agent-created intermediate milestone does not establish necessity.
- Minimize total time to the accepted user outcome, including reading, coding, delegation, review, verification and computation. Prefer changes with a demonstrated effect on that outcome over isolated percentage gains or more machinery. All phases and repair attempts share the user's elapsed-time allowance; a new assignment or milestone does not reset it. Review progress at least every 30 elapsed minutes, sooner when needed to protect the deadline: name the user acceptance condition advanced and its evidence. If none advanced, change the approach; bookkeeping and implementation activity alone do not count. After acceptance, integrate and continue within the authorized scope without another user prompt; reopen accepted work only for relevant new evidence.
- Make the smallest complete change that fits the existing design. Prefer simple interfaces that contain complexity, clear data ownership and derived state over wrappers and duplicated rules. Preserve required contracts; avoid speculative frameworks and unrelated cleanup.
- Diagnose the named defect before patching. Capture the original exception and relevant input identities, reproduction, resource measurements and affected contracts before implementation. Choose the cheapest observation that changes the repair decision; do not broaden diagnosis into an audit of unrelated code or the entire research catalogue. Consolidate the diagnosis into one fix pass, then one decisive verification pass. Error-capture instrumentation is diagnosis, not evidence that the underlying failure was fixed. If verification fails, preserve and report the evidence and reassess before further edits; do not automatically start another repair cycle.
- Verify the changed behavior with the cheapest decisive check plus required project checks. Use an independent expected result; add a failing regression test first when practical. Reuse accepted evidence while its relevant inputs and assumptions hold. Broaden or repeat checks for a new change, failure or unresolved risk. Engineering checks do not establish scientific completion.
- Batch independent reads and tool calls. For this project, use Grok through Cursor for delegated work; do not use native subagents. Give each Cursor assignment a clear outcome, relevant context, owned files, verification and a concise report; integrate its findings before declaring completion. Follow the project's selected implementation model and execution rules.
- Read the current checkpoint and relevant sources instead of restarting discovery. Update existing state with decisions, evidence pointers and remaining work; avoid duplicate manuals and audit files.
- Keep instructions lean. Add a rule only for a concrete recurring failure that existing guidance does not address; replace obsolete rules instead of accumulating them. Report the result, verification and material remaining gaps briefly.
